Overview

What This Document Defines

The FRD specifies what the system must do — not how. Each requirement is testable, traceable, and maps to a corresponding section in the Low Level Design (LLD).

FRD Answers

  • What must the kernel do?
  • What must the kernel guarantee?
  • What behaviors are required?
  • What are the acceptance criteria?
  • What is in scope vs. deferred?

FRD Does NOT Answer

  • Which data structures to use
  • Which algorithms to implement
  • How many lines of code
  • Internal API signatures
  • Performance targets (that's NFR)

Area A

A. Boot & CPU Control

Getting from power-on to kernel_main()

FR01 FR02 
Power On → BIOS → GRUB → _start (32-bit) → Long Mode (64-bit) → kernel_main()
Area A — Boot

FR01 — Multiboot Boot

FR01 Multiboot2 Boot P0

The kernel must boot via a Multiboot2-compliant bootloader (GRUB). The kernel binary must contain a valid Multiboot2 header so that GRUB can locate and load it.

Requirements

  • Kernel ELF contains Multiboot2 header in first 32KB
  • Header includes magic number 0xE85250D6
  • Kernel must accept Multiboot2 info structure from bootloader
  • Must parse memory map from Multiboot2 info
  • Must record kernel load address from Multiboot2 info

Acceptance Criteria

  • GRUB recognizes and loads the kernel ELF without error
  • Control reaches _start with EAX = 0x36D76289
  • EBX points to a valid Multiboot2 info structure
  • Memory map is accessible and contains at least one usable region

Test: qemu -kernel kernel.elf boots without triple fault

Area A — Boot

FR02 — Kernel Entry & Long Mode

FR02 Kernel Entry & CPU Initialization P0

The kernel entry point (_start) must transition the CPU from 32-bit Protected Mode to 64-bit Long Mode, set up a valid stack, and transfer control to C code (kernel_main).

Requirements

  • Set up initial stack pointer (ESP) before any function calls
  • Save Multiboot2 info pointer for later use
  • Create initial page tables (identity map + higher-half)
  • Enable PAE (CR4 bit 5)
  • Enable Long Mode (EFER.LME, MSR 0xC0000080)
  • Enable paging (CR0.PG)
  • Load 64-bit GDT and far-jump to 64-bit code
  • Set up 64-bit stack (RSP), clear BSS
  • Call kernel_main with Multiboot2 info as argument

Acceptance Criteria

  • CPU is in 64-bit Long Mode after _start completes
  • RSP points to a valid, aligned kernel stack
  • BSS section is zeroed
  • kernel_main() receives a valid pointer to Multiboot2 info
  • Identity mapping covers at least the first 2MB
  • Higher-half mapping at 0xFFFF800000000000 is functional

Test: kernel_main prints "Hello" to serial without faulting

Area B — Privilege

FR03 — Privilege Enforcement

FR03 CPU Privilege Enforcement P0

The kernel must run in Ring 0 and all user processes must run in Ring 3. The CPU's hardware privilege mechanism must enforce this separation.

Requirements

  • GDT must define separate code/data segments for Ring 0 and Ring 3
  • TSS must be configured with RSP0 (kernel stack for Ring 3→0 transitions)
  • User code must execute with CPL=3
  • Kernel code must execute with CPL=0
  • Privileged instructions (CLI, STI, IN, OUT, MOV CR3, LGDT, LIDT) must fault when executed from Ring 3

Acceptance Criteria

  • GDT loaded with null, kernel CS/DS, user CS/DS, and TSS entries
  • TSS.rsp0 is updated on every context switch
  • User thread executing cli triggers a General Protection fault (#GP)
  • User thread executing in al, 0x3F8 triggers #GP
  • Kernel can execute all privileged instructions without fault

Test: user thread runs privileged instruction → fault → thread killed → kernel continues

Area B — Privilege

FR04 — Syscall Handling

FR04 Syscall Entry & Return P0

The kernel must provide a controlled mechanism for user threads to request kernel services. The transition must validate inputs, switch stacks, and restore context on return.

Requirements

  • Use x86-64 syscall/sysret instructions
  • Configure MSRs: STAR, LSTAR, SFMASK
  • Syscall number passed in RAX
  • Arguments in RDI, RSI, RDX, R10
  • Return value in RAX
  • Kernel must save/restore user context
  • Kernel must switch to thread's kernel stack on entry
  • Kernel must validate all user-provided pointers and arguments

Acceptance Criteria

  • User calls syscall → arrives at kernel dispatch
  • Invalid syscall number → returns error code
  • Pointer outside user address range → returns error
  • After syscall, user thread resumes at correct instruction
  • All user registers (except RAX) are preserved

Test: user thread calls SYS_YIELD → kernel schedules → user resumes correctly

Area C

C. Physical Memory Management

Tracking and allocating real RAM frames

FR05 FR06 NEW in v3.0
This area was missing in FRD v2.0. Without physical memory management, the kernel cannot create page tables, allocate stacks, or manage address spaces.
Area C — Physical Memory

FR05 — Physical Frame Tracking

FR05 Physical Memory Discovery & Tracking P0

The kernel must discover available physical memory from the Multiboot2 memory map and maintain a data structure that tracks which 4KB physical frames are free or allocated.

Requirements

  • Parse Multiboot2 memory map to identify usable RAM regions
  • Mark frames occupied by kernel code/data as "used"
  • Mark BIOS/reserved regions as "used"
  • Track all remaining frames as "free"
  • Frame size: 4096 bytes (4KB), page-aligned

Acceptance Criteria

  • After initialization, free frame count > 0
  • Kernel code frames are marked used (not allocatable)
  • Reserved/MMIO regions are never returned as free
  • Total tracked memory matches Multiboot2 reported RAM

Test: print free frame count after init → matches expected value from memory map

Area C — Physical Memory

FR06 — Physical Frame Allocation

FR06 Frame Allocate & Free P0

The kernel must provide operations to allocate a free physical frame and to return an allocated frame to the free pool.

Requirements

  • alloc_frame() — returns physical address of a free 4KB frame, marks it used
  • free_frame(addr) — marks a used frame as free
  • Allocation of zero available frames must return an error (not crash)
  • Double-free must be detectable (debug builds)
  • Returned frames must be 4KB-aligned

Acceptance Criteria

  • Allocate N frames → free count decreases by N
  • Free N frames → free count increases by N
  • Allocate when empty → returns NULL/error
  • All returned addresses are 4KB-aligned
  • No frame is returned twice from consecutive allocs

Test: alloc 100 frames, verify unique addresses, free all, alloc again

Area D — Virtual Memory

FR07 — Independent Virtual Address Spaces

FR07 Per-Process Virtual Address Space P0

Each process must have its own independent virtual address space. The kernel must support creating, switching, and destroying address spaces.

Requirements

  • Each address space has its own PML4 (page table root)
  • Kernel must be able to create a new address space
  • Kernel must be able to switch active address space (load CR3)
  • Kernel must be able to destroy an address space (free all associated frames)
  • Address spaces must have unique identifiers

Acceptance Criteria

  • Creating two address spaces → they have different PML4 physical addresses
  • Switching address space → CR3 changes
  • Mapping virtual address V to physical P in space A → V resolves to P in space A
  • Same virtual address V in space B → resolves to different physical address

Test: create 2 spaces, map same VA to different PAs, switch, verify

Area D — Virtual Memory

FR08 — Memory Isolation

FR08 Inter-Process Memory Isolation P0

The kernel must guarantee that no process can access another process's memory, and no user process can access kernel memory.

Requirements

  • User pages must have U/S bit = 1 (user accessible)
  • Kernel pages must have U/S bit = 0 (supervisor only)
  • User access to kernel-mapped address → page fault
  • User access to unmapped address → page fault
  • Separate page tables prevent cross-process access

Acceptance Criteria

  • User thread reads kernel address → #PF → thread killed → kernel continues
  • User thread writes kernel address → #PF → thread killed → kernel continues
  • User thread accesses address 0x0 (NULL) → #PF → thread killed
  • Thread in space A cannot read memory belonging to space B

Test: user thread dereferences kernel pointer → fault → thread killed

Area D — Virtual Memory

FR09 — Page Table Management

FR09 Page Table Map / Unmap P0

The kernel must be able to map a virtual address to a physical frame and unmap it, in any address space.

Requirements

  • map(vaddr, paddr, flags) — create PTE mapping
  • unmap(vaddr) — remove PTE, invalidate TLB entry
  • Flags: read-only, read-write, user/supervisor, no-execute
  • Intermediate page table levels (PDPT, PD, PT) must be allocated on demand
  • TLB must be flushed when mappings change (invlpg)

Acceptance Criteria

  • Map VA → PA → read VA → get data at PA
  • Unmap VA → read VA → page fault
  • Map VA as read-only → write VA → page fault
  • Map VA as NX → execute VA → page fault
  • Map VA as supervisor-only → user access → page fault

Test: map, read, unmap, read → fault

Area D — Virtual Memory

FR10 — Kernel Memory Protection

FR10 Higher-Half Kernel Mapping P0

Kernel code and data must be mapped in the higher half of the virtual address space, shared across all address spaces, and protected from user access.

Requirements

  • Kernel mapped starting at 0xFFFF800000000000
  • Kernel mapping present in every address space's PML4
  • Kernel pages: U/S = 0, so Ring 3 cannot access
  • Kernel code pages: NX = 0 (executable)
  • Kernel data pages: NX = 1 (not executable)
  • First page (address 0x0) must remain unmapped (NULL guard)

Acceptance Criteria

  • After switching to any address space, kernel code still runs correctly
  • Kernel can access its own data via higher-half addresses
  • User code at any address < 0x0000800000000000 cannot read kernel memory
  • NULL dereference (read or write at address 0) → page fault

Test: switch CR3 to user space → kernel continues → switch back → still works

Area D — Virtual Memory

FR11 — Page Fault Handling

FR11 Page Fault Handler P0

The kernel must handle page fault exceptions (vector 14). In Phase 1, all user page faults terminate the faulting thread. The handler must not crash the kernel.

Phase 1 Requirements

  • Register handler for IDT vector 14
  • Read faulting address from CR2
  • Read error code (pushed by CPU): P, W/R, U/S bits
  • If fault from user mode → kill thread, log fault details
  • If fault from kernel mode → kernel panic

Phase 2 (Deferred)

  • Deliver page fault to user-space pager via IPC
  • Pager resolves fault (demand paging, swap)
  • Kernel resumes faulting thread if pager succeeds

Acceptance Criteria

  • User null deref → thread killed → kernel continues
  • Kernel null deref → panic with register dump

Test: user touches unmapped address → fault logged → thread gone → scheduler runs

Area E

E. Threading

Execution contexts, lifecycle, and context switching

FR12 FR13 FR14 FR15
Thread = execution context (registers + stack + state). Address Space = memory ownership. A thread does NOT own its page tables — the address space does.
Area E — Threading

FR12 — Thread Creation

FR12 Create Execution Thread P0

The kernel must be able to create new threads. Each thread has its own registers, kernel stack, user stack, and initial state.

Requirements

  • Allocate unique thread ID
  • Allocate kernel stack (for syscall/interrupt handling)
  • Set initial instruction pointer to entry function
  • Set initial stack pointer to allocated user stack
  • Associate thread with an address space
  • Set initial state to RUNNABLE
  • Enqueue in scheduler's run queue

Acceptance Criteria

  • Created thread has unique ID ≠ any existing thread
  • Thread starts executing at specified entry point
  • Thread runs in specified address space
  • Thread appears in run queue after creation
  • Creating a thread does not disrupt currently running thread

Test: create thread with entry=test_func → scheduler eventually runs it → output observed

Area E — Threading

FR13 — Thread States

FR13 Thread State Model P0

Every thread must be in exactly one of three states at all times. State transitions must follow the defined state machine.

States

StateMeaningLocation
RUNNINGExecuting on CPUcurrent_thread pointer
RUNNABLEReady for CPURun queue
BLOCKEDWaiting for eventIPC send queue

Valid Transitions

  • RUNNABLE → RUNNING (scheduler picks thread)
  • RUNNING → RUNNABLE (preemption or yield)
  • RUNNING → BLOCKED (IPC send/recv with no partner)
  • BLOCKED → RUNNABLE (partner arrives, wakeup)

Invalid Transitions

  • BLOCKED → RUNNING (must go through RUNNABLE)
  • RUNNABLE → BLOCKED (must be RUNNING first)
Area E — Threading

FR14 — Context Switching

FR14 Save & Restore Execution Context P0

The kernel must be able to save the full execution context of the current thread and restore the context of another thread, so each thread runs as if it were never interrupted.

Requirements

  • Save callee-saved registers: RBX, RBP, R12, R13, R14, R15
  • Save/restore RSP (stack pointer)
  • CPU automatically saves/restores: RIP, CS, RFLAGS, RSP, SS (interrupt frame)
  • Update TSS.rsp0 to new thread's kernel stack top
  • If address space differs: load new CR3
  • Interrupts must be disabled during switch

Acceptance Criteria

  • Thread A runs → timer → switch to B → timer → switch to A → A continues from exact point
  • Thread's local variables on stack are preserved across switch
  • All registers restored to pre-switch values
  • No stack corruption after 1000+ context switches

Test: two threads increment separate counters → both reach expected values

Area E — Threading

FR15 — Thread Destruction

FR15 Thread Exit & Cleanup P0 NEW in v3.0

The kernel must support thread termination. When a thread exits or is killed, all resources it holds must be properly released.

Requirements

  • Thread can voluntarily exit via SYS_EXIT
  • Kernel can kill thread on unrecoverable fault
  • On death: remove from run queue or IPC queue
  • On death: free kernel stack
  • On death: wake threads blocked trying to send to this thread (with error)
  • If last thread in address space → destroy address space

Acceptance Criteria

  • Thread calls SYS_EXIT → never scheduled again
  • Kernel stack memory is reclaimed
  • Thread blocked sending to dead thread → unblocked with error code
  • Thread ID is not reused immediately (or never)
  • Scheduler handles thread death during its timeslice

Test: create thread → it exits → memory freed → no dangling references

Area F — Scheduling

FR16 — Round Robin Scheduler

FR16 Round Robin Scheduling P0

The kernel must schedule threads using a Round Robin policy. Each thread gets an equal timeslice. Preemption is driven by the hardware timer interrupt.

Requirements

  • FIFO run queue: enqueue at tail, dequeue from head
  • Timer interrupt triggers schedule decision
  • Current thread's timeslice expires → enqueue at tail, pick head
  • Thread can voluntarily yield (SYS_YIELD)
  • Blocking (IPC) removes thread from run queue entirely
  • Wakeup inserts thread at tail of run queue

Acceptance Criteria

  • 3 threads → each gets roughly equal CPU time
  • Thread yields → next thread runs immediately
  • Thread blocks on IPC → skipped, next RUNNABLE runs
  • Thread wakes from IPC → appears at tail of queue
  • No thread starvation (all RUNNABLE threads eventually run)

Test: 3 threads print IDs → output shows interleaved, fair scheduling

Area F — Scheduling

FR17 — Idle Thread

FR17 Idle Thread P0 NEW in v3.0

The system must have an idle thread that runs when no other thread is RUNNABLE. The idle thread puts the CPU in a low-power state until the next interrupt.

Requirements

  • Idle thread is created at boot, always exists
  • Idle thread runs only when run queue is empty
  • Idle thread executes hlt in a loop
  • Idle thread must be interruptible (IF=1)
  • Idle thread is never killed or destroyed
  • Idle thread does not count toward thread scheduling fairness

Acceptance Criteria

  • All threads block on IPC → idle thread runs → CPU halts
  • Timer interrupt fires → idle thread yields → if thread woke, it runs
  • System does not crash or busy-loop when no work exists
  • CPU power consumption drops during idle (measurable in QEMU via host CPU usage)

Test: all threads exit → idle thread runs → system stable → no CPU spin

Area G

G. Inter-Process Communication (IPC)

The microkernel's core communication mechanism

FR18 FR19 FR20
In a microkernel, IPC performance = system performance. Every driver call, every service request, every interrupt delivery goes through IPC.
Area G — IPC

FR18 — Synchronous IPC

FR18 Synchronous Send & Receive P0

The kernel must provide synchronous IPC primitives: send() and recv(). Both operations block the calling thread if the communication cannot complete immediately.

Send Requirements

  • send(target_tid, msg)
  • If receiver is blocked in recv() → transfer immediately, wake receiver
  • If receiver is NOT in recv() → block sender, enqueue on receiver's send_queue
  • Message is copied (not pointer-shared)
  • Sender does not resume until message is delivered

Receive Requirements

  • recv(buffer)
  • If sender is queued → dequeue, copy message to buffer, wake sender
  • If no sender queued → block receiver
  • Receiver buffer must be validated (in user address space)
  • If message > buffer → return error, no truncation

Test: thread A sends to B → B receives → message content matches

Area G — IPC

FR19 — IPC Queues & Message Format

FR19 IPC Queue Model & Fixed Messages P0

Each thread that can receive messages owns a sender queue. Messages are fixed-size (64 bytes) and stored inside the blocked sender's thread struct.

Queue Requirements

  • Multiple senders can queue on one receiver
  • Receiver's send_queue is a linked list of blocked sender threads
  • Each sender has waiting_for pointing to receiver
  • FIFO order: first sender to arrive is first to be dequeued
  • Dequeued sender is set to RUNNABLE and enqueued in run queue

Message Requirements

  • Fixed size: 64 bytes total
  • Fields: sender_id (int), msg_type (int), data (56 bytes)
  • Message stored inside thread.pending_msg
  • No kernel heap allocation for messages
  • No global IPC buffer pool

Test: 3 senders → 1 receiver → receiver gets all 3 messages in FIFO order

Area G — IPC

FR20 — Deferred Wakeup

FR20 Deferred Wakeup Policy P0

When an IPC operation wakes a blocked thread, the kernel must not immediately switch to that thread. The woken thread is enqueued as RUNNABLE, and the scheduler decides when it actually runs.

Requirements

  • Wakeup = state change (BLOCKED → RUNNABLE) + enqueue in run queue
  • Wakeup does NOT trigger immediate context switch
  • Scheduler makes all scheduling decisions
  • The currently running thread continues its timeslice after waking another thread

Why This Matters

  • Keeps scheduler as single authority for CPU allocation
  • Prevents IPC from bypassing fairness
  • Simplifies reasoning about preemption
  • Avoids nested context switches

Test: A recv() wakes B → A continues running → B runs later on its own timeslice

Area I — Interrupts

FR22 — Interrupt Handling

FR22 IDT & Interrupt Dispatch P0

The kernel must set up the Interrupt Descriptor Table (IDT) and handle all CPU exceptions and hardware interrupts. Unhandled interrupts must not crash the kernel.

Requirements

  • Initialize IDT with 256 entries
  • Register handlers for exceptions 0–31
  • Register handlers for hardware IRQs (remapped to vectors 32+)
  • Initialize PIC (8259) or APIC for interrupt routing
  • Double fault (vector 8) must use IST (separate stack)
  • All handlers must send EOI (End of Interrupt) to PIC/APIC
  • Unknown/spurious interrupts must be safely ignored

Acceptance Criteria

  • Division by zero in user → exception caught → thread killed
  • Timer interrupt fires at expected frequency
  • Serial IRQ arrives → handler runs → data available
  • Stack overflow in kernel → double fault on IST stack → panic (not triple fault)
  • Spurious IRQ → ignored, no crash

Test: enable interrupts → timer fires → handler runs → system continues

Area I — Interrupts

FR23 — Hardware Timer

FR23 Periodic Timer Interrupt P0

The kernel must configure a hardware timer to generate periodic interrupts. These interrupts drive the scheduler's preemption mechanism.

Requirements

  • Configure PIT (Programmable Interval Timer) or APIC timer
  • Timer fires at a configurable frequency (initial: ~100 Hz)
  • Each timer tick increments a global tick counter
  • Timer handler invokes scheduler to check timeslice
  • Timer is the primary preemption source

Acceptance Criteria

  • Timer interrupt fires repeatedly at configured rate
  • Global tick counter increments monotonically
  • A CPU-bound thread is preempted after its timeslice
  • Timer works correctly even when switching between threads

Test: single thread loops forever → timer fires → tick count increases → observable on serial

Area J

J. Drivers, Safety & Observability

User-space drivers, fault isolation, and debugging

FR24 FR25
Area J — Drivers & Safety

FR24 — User-Space Driver Model

FR24 Driver Architecture & Interrupt Forwarding P0

Device drivers must run as user-space processes. The kernel must provide mechanisms for drivers to access I/O ports and receive hardware interrupt notifications via IPC.

Requirements

  • Drivers run in Ring 3 (user space)
  • Driver requests I/O port access via SYS_MAP_IO
  • Kernel grants per-thread I/O port permission (via IOPB in TSS)
  • Driver registers for IRQ via SYS_IRQ_REG
  • When IRQ fires: kernel masks IRQ, sends IPC notification to registered thread
  • Driver acknowledges via SYS_IRQ_ACK → kernel unmasks IRQ
  • First driver: Serial (UART, COM1, base 0x3F8, IRQ 4)

Acceptance Criteria

  • Serial driver process runs in user space
  • Serial driver can read/write COM1 ports
  • Serial input triggers IRQ → kernel IPC → driver receives byte
  • Driver crash → kernel continues, other threads unaffected
  • No driver can access ports it hasn't been granted

Test: type in QEMU serial → driver receives chars → echoes back

Area J — Drivers & Safety

FR25 — Fault Isolation, Panic & Logging

FR25 System Stability & Observability P0

The kernel must survive any user-space fault, halt safely on kernel faults, and provide serial output for debugging.

Fault Isolation

  • User process crash must not affect kernel
  • User process crash must not affect other processes
  • Killed thread's IPC dependents must be notified (error)

Kernel Panic

  • On unrecoverable kernel error: disable interrupts
  • Print error message to serial
  • Print register dump (RIP, RSP, CR2, error code)
  • Halt CPU in loop (never returns)

Serial Logging

  • Kernel outputs debug info on COM1 (0x3F8)
  • Available from earliest boot (first init in kernel_main)
  • Must work before any other subsystem

Test: crash user thread → log on serial → kernel running
