Foundations

What is a Microkernel?

A microkernel runs the absolute minimum in kernel mode. Everything else — drivers, filesystems, networking — runs as user-space processes communicating via IPC.

Kernel provides MECHANISMS

  • Context switching
  • Memory protection
  • IPC message passing
  • Interrupt routing
  • Privilege enforcement

User space provides POLICIES

  • Device drivers
  • Filesystem
  • Networking stack
  • Process management
  • Security policies

CPU & Privilege

CPU Privilege Rings

x86-64 has 4 privilege rings (0–3). We use only Ring 0 (kernel) and Ring 3 (user). The CPU hardware enforces this — it's not software convention.
    ┌───────────────┐
    │    Ring 3      │ ← User processes
    │  (Restricted)  │   Cannot:
    │                │   • Access I/O ports
    │   ┌───────┐    │   • Modify page tables
    │   │Ring 0 │    │   • Disable interrupts
    │   │Kernel │    │   • Execute privileged
    │   │(Full  │    │     instructions
    │   │Access)│    │
    │   └───────┘    │
    └───────────────┘

Ring 0 — Kernel

  • Full hardware access
  • Can modify page tables (CR3)
  • Can enable/disable interrupts
  • Can execute IN/OUT (I/O ports)

Ring 3 — User

  • Cannot touch hardware
  • Cannot see other processes' memory
  • Must use syscalls to request services

  • No paging (your page tables)

Boot Process

_start — Assembly Bootstrap (32-bit → 64-bit)

; Step 1: Set up temporary stack
    mov esp, stack_top          ; now C calling convention works

; Step 2: Save multiboot pointer
    mov [multiboot_ptr], ebx

; Step 3: Set up page tables for long mode
    ; Identity map first 2MB    (so current code keeps running)
    ; Map higher-half kernel    (0xFFFF800000000000+)

; Step 4: Enable PAE in CR4
    mov eax, cr4
    or  eax, (1 << 5)           ; CR4.PAE = 1
    mov cr4, eax

; Step 5: Load page table root into CR3
    mov eax, pml4_table
    mov cr3, eax

; Step 6: Enable long mode (set EFER.LME)
    mov ecx, 0xC0000080         ; EFER MSR
    rdmsr
    or  eax, (1 << 8)           ; LME bit
    wrmsr

; Step 7: Enable paging (CR0.PG = 1)
    mov eax, cr0
    or  eax, (1 << 31)
    mov cr0, eax

; Step 8: Load 64-bit GDT and far jump to 64-bit code
    lgdt [gdt64.pointer]
    jmp  gdt64.code_segment:long_mode_start

Boot Process

kernel_main() — First C Code

void kernel_main(multiboot_info_t *mbi) {

    serial_init();            // 1. Debug output first — see what's happening

    gdt_init();               // 2. Proper GDT with TSS (for ring transitions)

    idt_init();               // 3. Interrupt Descriptor Table (exception + IRQ handlers)

    pmm_init(mbi);            // 4. Physical Memory Manager (parse memory map)

    vmm_init();               // 5. Virtual Memory Manager (kernel page tables)

    scheduler_init();         // 6. Scheduler (create idle thread)

    thread_create(init_task); // 7. First real user thread

    scheduler_start();        // 8. Enable timer, start scheduling (never returns)
}
Order matters! Each step depends on the previous one. Serial first = you can debug everything after it. GDT before IDT = interrupts need valid segments.

CPU Structures

GDT & TSS — Segment and Stack Control

GDT (Global Descriptor Table)

Defines memory segments. In 64-bit, segmentation is mostly flat, but GDT is still required for:

EntryPurpose
0x00Null descriptor (required)
0x08Kernel Code (Ring 0, 64-bit)
0x10Kernel Data (Ring 0)
0x18User Code (Ring 3, 64-bit)
0x20User Data (Ring 3)
0x28TSS descriptor

TSS (Task State Segment)

When CPU transitions Ring 3 → Ring 0, it needs to know which kernel stack to use. TSS provides this.

struct tss {
    uint32_t reserved0;
    uint64_t rsp0;  // ← kernel stack
    uint64_t rsp1;
    uint64_t rsp2;
    // ... IST entries ...
};
On every context switch, kernel updates TSS.rsp0 to point to the new thread's kernel stack top.

IDT — Interrupt Descriptor Table

256 entries. Each entry tells the CPU: "when interrupt N fires, jump to this handler at this privilege level."

VectorTypeNameOur Action
0ExceptionDivide ErrorKill thread
6ExceptionInvalid OpcodeKill thread
8ExceptionDouble FaultKernel panic (use IST)
13ExceptionGeneral ProtectionKill thread
14ExceptionPage FaultHandle or kill
32IRQ 0Timer (PIT/APIC)Schedule
33IRQ 1KeyboardIPC → driver
36IRQ 4Serial (COM1)IPC → serial driver
128SyscallSoftware interruptSyscall dispatch
Double fault (vector 8) uses a separate stack via IST to avoid a triple fault if the kernel stack itself overflows.

Memory Architecture

Physical Memory Manager — Frame Allocator

Tracks which 4KB physical frames are free or used. Kernel-only. This is where all physical memory allocation starts.

Bitmap Allocator (Our Choice)

Frame:  0  1  2  3  4  5  6  7
Bitmap: 1  1  1  0  0  1  0  0
        ↑        ↑     ↑
      kernel   free  allocated
       code         by thread

alloc_frame()
  → scan for first 0
  → set to 1, return address

free_frame(addr)
  → set bit to 0

Why Bitmap?

  • Simple — one bit per 4KB frame
  • Deterministic allocation time
  • Easy to initialize from GRUB memory map
  • Good enough for our scale

Interface

void     pmm_init(multiboot_info);
void*    pmm_alloc_frame();
void     pmm_free_frame(void* addr);

Memory Architecture

x86-64 Paging — 4-Level Page Tables

Virtual Address (48 bits used):
┌────────┬────────┬────────┬────────┬────────────┐
│ PML4   │ PDPT   │  PD    │  PT    │  Offset    │
│ 9 bits │ 9 bits │ 9 bits │ 9 bits │  12 bits   │
└───┬────┴───┬────┴───┬────┴───┬────┴────────────┘
    │        │        │        │
    ▼        ▼        ▼        ▼
  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
  │PML4 │→│PDPT │→│ PD  │→│ PT  │→ Physical Frame + Offset
  │Table│ │Table│ │Table│ │Table│
  └─────┘ └─────┘ └─────┘ └─────┘
    512     512     512     512     = 256 TB addressable
  entries entries entries entries

Each entry: 64 bits
  ├── Physical address of next table (bits 12-51)
  ├── Present bit (P)       — is this entry valid?
  ├── Read/Write bit (R/W)  — writable?
  ├── User/Supervisor (U/S) — Ring 3 accessible?
  └── No-Execute (NX)       — executable?
The U/S bit is how the CPU enforces memory isolation. Kernel pages have U/S=0, so Ring 3 code faults when touching them.

Threading

Thread — The Schedulable Unit

CPU schedules execution, not memory ownership. Thread = execution context. Address Space = memory.

Thread Structure

struct thread {
    int id;
    enum thread_state state;

    void *rsp;
    void *kernel_stack_top;

    struct thread *next;

    // IPC
    struct thread *waiting_for;
    struct thread *send_queue;
    struct ipc_message pending_msg;

    // Memory
    struct address_space *addr_space;
};

What a Thread Owns

  • Registers — RAX..R15, RFLAGS
  • Stack pointer — RSP (saved/restored)
  • Kernel stack — for syscall/interrupt handling
  • State — RUNNING / RUNNABLE / BLOCKED
  • IPC state — pending message, queues

What a Thread Shares

  • Address space (with sibling threads)
  • Code and heap mappings

Scheduling

Round Robin Scheduler

Run Queue (FIFO)

struct run_queue {
    struct thread *head;
    struct thread *tail;
};

Visually:
HEAD → [T1] → [T2] → [T3] → NULL
                              ↑
                             TAIL

Scheduler Flow

Timer Interrupt fires
    │
    ▼
current→state = RUNNABLE
enqueue(current) at tail
    │
    ▼
next = dequeue() from head
next→state = RUNNING
    │
    ▼
context_switch(current, next)

Invariants (MUST hold)

  • RUNNING thread is never in run queue
  • Only RUNNABLE threads in run queue
  • BLOCKED threads are never scheduled
  • Each thread in exactly one place

Idle Thread

When run queue is empty, schedule the idle thread which executes hlt in a loop — puts CPU in low-power state until next interrupt.
void idle_thread() {
    while(1) {
        asm("hlt");
    }
}

Context Switching

Context Switch — The Core Mechanism

What gets saved/restored per thread:

Callee-saved registers (your code saves):
    RBX, RBP, R12, R13, R14, R15, RSP

Interrupt frame (CPU saves automatically):
    RIP, CS, RFLAGS, RSP, SS


The actual switch:

Thread A (RUNNING)                    Thread B (was RUNNABLE)
     │                                     ▲
     ▼                                     │
 Save RBX, RBP, R12-R15              Restore RBX, RBP, R12-R15
     │                                     ▲
     ▼                                     │
 A→rsp = current RSP ──── swap ────► RSP = B→rsp
     │                                     ▲
     ▼                                     │
 Update TSS.rsp0 = B→kernel_stack_top      │
     │                                     │
     ▼                                     │
 Switch CR3 if different address space     │
     │                                     │
     └─────────────► iretq ───────────────┘
                   (restores RIP, RFLAGS, RSP, CS, SS)

Context Switching

Context Switch — CPU-Level Detail

Step-by-step: what happens when timer fires while Thread A runs in user mode

 1. Hardware timer fires IRQ 0
         │
 2. CPU detects interrupt:
    ├── Reads IDT[32] → gets handler address, target CS (kernel)
    ├── Privilege change (Ring 3 → Ring 0):
    │     └── Loads RSP from TSS.rsp0 (Thread A's kernel stack)
    └── CPU pushes onto kernel stack:
              SS          ← user stack segment
              RSP         ← user stack pointer
              RFLAGS      ← user flags
              CS          ← user code segment
              RIP         ← user instruction pointer (return address)
         │
 3. Your interrupt stub (ASM) runs:
    ├── push all general registers (RAX, RBX, ... R15)
    ├── call scheduler_tick()     ← C code
         │
 4. Scheduler decides to switch:
    ├── A→rsp = current RSP (points to saved registers on kernel stack)
    ├── A→state = RUNNABLE, enqueue(A)
    ├── B = dequeue(), B→state = RUNNING
    ├── RSP = B→rsp (now on B's kernel stack, with B's saved registers)
    ├── TSS.rsp0 = B→kernel_stack_top
    └── CR3 = B→addr_space→pml4 (if different)
         │
 5. Interrupt stub restores:
    ├── pop all general registers (from B's stack now!)
    └── iretq → pops RIP, CS, RFLAGS, RSP, SS
              → CPU now executing Thread B in Ring 3

IPC Design

IPC — The Microkernel's Nervous System

In a microkernel, everything communicates via IPC. App → FS → Disk Driver: every arrow is an IPC message. Performance of IPC = performance of the entire system.

Synchronous

Sender blocks until receiver gets the message

Our choice ✓
  • Simple
  • No kernel buffering
  • Deterministic

Fixed-Size Messages

Every message is the same size (e.g., 64 bytes)

Our choice ✓
  • No malloc in kernel
  • Predictable
  • Simple validation

Copy-Based

Message data is copied, not shared via pointers

Our choice ✓
  • Full isolation
  • No shared memory bugs
  • Easy to validate

IPC Design

IPC Message Structure

Message Format

#define IPC_MSG_DATA_SIZE 56

struct ipc_message {
    int      sender_id;
    int      msg_type;
    uint8_t  data[IPC_MSG_DATA_SIZE];
};

// Total: 64 bytes (fits in cache line)

Ownership Rule

Message is stored inside the blocked sender's thread struct. No global IPC buffers. No kernel allocation.

Why This Works

Thread T1 (BLOCKED, waiting to send)
 └── thread.pending_msg = {
         sender_id: 1,
         msg_type:  MSG_WRITE,
         data:      [...]
     }

Thread T2 (BLOCKED, waiting to send)
 └── thread.pending_msg = {
         sender_id: 2,
         msg_type:  MSG_READ,
         data:      [...]
     }

Receiver B:
 └── B.send_queue → T1 → T2 → NULL

Error Policy

If message > receiver buffer: ERROR (no truncation)

IPC Queue Architecture

Receiver-owned sender queue model:

Each thread that can receive has a send_queue:

  Thread B (Receiver):
       B.send_queue → [T1] → [T2] → [T3] → NULL

  T1.waiting_for = B
  T2.waiting_for = B

IPC Flows

IPC Case 1: Send → Receiver NOT Ready

Thread A calls: ipc_send(B, &msg)
         │
         ▼
Kernel checks: Is B blocked in recv()?
         │
         ▼
    NO — B is not waiting for a message
         │
         ▼
Kernel actions:
    1. A.state = BLOCKED
    2. A.waiting_for = B
    3. A.pending_msg = msg  (copy message into A's struct)
    4. Append A to B.send_queue
    5. Remove A from scheduler
         │
         ▼
Scheduler picks next RUNNABLE thread
         │
         ▼
A stays blocked until B calls recv()
29 / 45
IPC Flows

IPC Case 2: Recv → Sender Available

Thread B calls: ipc_recv(&buf)
         │
         ▼
Kernel checks: Is B.send_queue empty?
         │
         ▼
    NO — There are senders waiting!
         │
         ▼
Kernel actions:
    1. sender = dequeue(B.send_queue)
    2. Copy sender.pending_msg → B's buffer  (the actual data transfer)
    3. sender.state = RUNNABLE
    4. sender.waiting_for = NULL
    5. Enqueue sender in run queue
    6. B continues running (already RUNNING)
         │
         ▼
Both threads can now proceed
Deferred wakeup: Kernel does NOT immediately switch to the woken sender. The scheduler decides when it actually runs. This keeps the scheduler in control.

Syscalls

Syscall Flow — Step by Step

User code:
    mov rax, 0          ; SYS_SEND
    mov rdi, target_tid
    mov rsi, msg_ptr
    syscall             ; CPU transfers control

CPU (hardware, automatic):
    1. RCX = return RIP (saved for sysret)
    2. R11 = RFLAGS (saved for sysret)
    3. RIP = LSTAR MSR value (your syscall entry point)
    4. CS  = STAR MSR kernel code segment
    5. SS  = STAR MSR kernel data segment
    // NOTE: RSP is NOT switched! You must do this manually.

Kernel entry (assembly):
    swapgs              ; access per-CPU data (get kernel stack)
    save user RSP
    load kernel RSP from TSS
    push all registers
    call syscall_dispatch

Kernel (C):
    switch(rax) {
        case SYS_SEND:  validate(rdi, rsi); ipc_send(...); break;
        case SYS_RECV:  validate(rdi);      ipc_recv(...); break;
        ...
    }

Return:
    pop all registers
    restore user RSP
    swapgs
    sysretq             ; CPU: RIP=RCX, RFLAGS=R11, back to Ring 3

Interrupt → IPC — Device Events to User Space

How a hardware event reaches a user-space driver:

 Serial port receives byte
         │
         ▼
 Hardware raises IRQ 4 → IDT vector 36
         │
         ▼
 Kernel interrupt handler:
    1. Acknowledge interrupt (EOI)
    2. Mask this IRQ (prevent storms)
    3. Look up: which thread registered for IRQ 4?
    4. Send lightweight IPC notification to that thread
         │
         ▼
 Serial driver thread (user space):
    was BLOCKED in recv()
    now RUNNABLE with notification message
         │
         ▼
 Driver wakes up:
    1. Read serial port data (via SYS_MAP_IO)
    2. Process data
    3. Unmask IRQ (SYS_IRQ_ACK)
    4. Go back to recv() — wait for next interrupt
The kernel never interprets device data. It just routes the interrupt signal. The driver (in user space) does all the real work.

Drivers

User-Space Driver Architecture

Why User-Space Drivers?

  • Fault isolation — driver crash ≠ kernel crash
  • Restartable — just respawn the process
  • Debuggable — regular user process, use normal tools
  • Smaller kernel — less code in Ring 0

Cost

  • Extra IPC overhead per I/O operation
  • Context switch to reach driver
For our scale, the overhead is negligible. Correctness > raw throughput.

Serial Driver (First Target)

// User-space serial driver
void serial_driver() {
    // Request I/O port access
    sys_map_io(0x3F8, 8);

    // Register for IRQ 4
    sys_irq_register(4);

    while (1) {
        // Block until interrupt
        msg = sys_recv();

        // Handle the I/O
        byte = inb(0x3F8);
        process(byte);

        // Acknowledge IRQ
        sys_irq_ack(4);
    }
}

Limitations

Known Limitations & Future Work

Known Issues

  • Deadlock — A→send(B), B→send(A). No detection yet.
  • No priority — Round Robin only. Priority inversion possible later.
  • Single core — No SMP support. One CPU only.
  • No demand paging — All memory pre-allocated.
  • No thread destruction cleanup — IPC queues may dangle.

Future Phases

  • Phase 2: Page fault handler + user pager
  • Phase 3: Priority scheduler
  • Phase 4: Filesystem server
  • Phase 5: Network stack
  • Phase 6: SMP (multi-core)
  • Phase 7: Capability-based security
